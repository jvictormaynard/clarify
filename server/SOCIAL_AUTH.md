# Google, Microsoft and GitHub native sign-in

The server supports all three providers for Clarify desktop and iOS. The app
uses a browser for provider consent. Provider client secrets and provider tokens
never enter a native client. Allauth 65.19.7 owns OAuth state, provider PKCE,
code exchange, social identities, signup, email verification and sessions.
The handoff table only transports an allauth session once to its initiating app.
Existing email-code login and account caches keep their existing contracts.

## Server configuration and provider registration

Use separate Web OAuth apps for staging and production. Set each ID/secret pair
from `.env.example` in the server secret store. An empty or incomplete pair
disables that provider and returns controlled `400 social_login_failed` on start.
The settings-based app is authoritative; do not also create database SocialApp
entries for that provider. Do not put provider secrets in desktop or iOS builds.

Register these exact production callback URLs, including the trailing slash:

| Provider | Web callback | Scopes |
| --- | --- | --- |
| Google | `https://clarify-api.victormaynard.com/accounts/google/login/callback/` | `profile email` |
| Microsoft | `https://clarify-api.victormaynard.com/accounts/microsoft/login/callback/` | delegated Microsoft Graph `User.Read` |
| GitHub | `https://clarify-api.victormaynard.com/accounts/github/login/callback/` | `user:email` |

For another deployment, replace only the HTTPS origin with its API origin. The
callback must use the same host as the native start request. Add that explicit
host to `ALLOWED_HOSTS`. The TLS proxy must overwrite forwarded headers. Do not
register the administration host or `clarify://` as a provider callback.

Google: create an OAuth client of type **Web application**. Configure the consent
screen, test users and publishing/verification state. This is server code exchange;
an iOS client ID is not used by this path. No Google JavaScript SDK is used.

Microsoft: create a Web platform registration that supports **Accounts in any
organizational directory and personal Microsoft accounts**. Use the `common`
tenant endpoint. Configure delegated Graph `User.Read` and the client secret.
Do not request offline access, mail, calendar, application permissions or a
tenant-specific endpoint. The Graph email field is not evidence of verified
email. A new Microsoft user must complete Clarify's email code verification.

GitHub: create an OAuth App, with the API origin as its homepage and the exact
callback above. `user:email` lets allauth retrieve private primary addresses and
their verified flag. Missing usable email is `social_email_required`. Organization
restrictions and private-email consent still require manual acceptance.

All three authorization requests use S256 provider PKCE. These provider verifiers
are generated by allauth and are separate from the native handoff verifier.
Provider access/refresh tokens are not stored (`SOCIALACCOUNT_STORE_TOKENS=False`).
There is no automatic email-based authentication or account linking. A new social
identity with an email already in Clarify returns `social_account_exists`; the
client must direct the user to email login. Existing linked social identities
can log in while signup is closed. New identities use `CLARIFY_SIGNUP_ENABLED`
and the existing per-peer/global signup and daily-email limits. Active-user and
verified-primary-email checks remain in force. Hosted processing quotas do not
change.

An unverified social identity is kept only in its allauth pending login stage.
Its usable SocialAccount link is deferred until that same stage completes email
verification. Independent email login cannot activate an abandoned social link.
Pending sessions contain no provider token or provider PKCE verifier. Mail
transport failures finish with `social_login_failed`; allauth confirmation limits
retain the native `429` response.

## Native protocol

Use HTTPS and JSON. Generate a new cryptographically random RFC7636 verifier
(43–128 ASCII unreserved characters) for every attempt. Keep it in app memory.
Compute `base64url(SHA256(verifier))`, without padding, as `code_challenge`.
Do not send a verifier to start, put it in a browser URL or persist it in logs.

1. `POST /_allauth/app/v1/auth/social/start` with exactly
   `{"provider":"google"|"microsoft"|"github","client":"desktop"|"ios","code_challenge":"..."}`.
   Success is `200 {"attempt_id":"<UUID>","authorization_url":"<same-origin HTTPS URL>","expires_in":300,"interval":5}`.
2. Open that URL in the system browser. The page requires a user action and a
   CSRF-protected POST before it starts OAuth. It warns the user to continue only
   for a sign-in started on this device. Allauth state and a private browser
   binding associate the provider callback with that exact attempt. No arbitrary
   `next`, provider parameters, callback URL or process can be supplied.
   The confirmation response ends the form navigation before opening the
   provider, so the strict form-action CSP also permits federated provider login.
3. Poll `POST /_allauth/app/v1/auth/social/poll` with exactly
   `{"attempt_id":"...","code_verifier":"..."}`. Wait at least five seconds
   between pending polls and honor `429`. Stop at the five-minute deadline.
4. `202` means pending. `200 {"meta":{"is_authenticated":true,"session_token":"..."}}`
   returns the native allauth session exactly once. Use `X-Session-Token` as for
   email login. A replay is `410`.
5. `401 {"meta":{"is_authenticated":false,"session_token":"..."},"data":{"pending":"signup","email":"..."}}`
   returns a pending allauth email-verification session exactly once. Save the
   token and email, show the existing signup code form, and submit the six-digit
   `key` to `POST /_allauth/app/v1/auth/email/verify` with `X-Session-Token`.
   Use the existing email-verification resend route if needed. This pending
   token grants no account/API access before verification.
6. Terminal `400` codes are `social_login_failed`, `social_account_exists`,
   `social_signup_closed` and `social_email_required`. Show fixed client copy;
   never display provider exception bodies. Expired, cancelled, unknown or
   consumed attempts return `410`. Limits return `429` (a terminal signup/email
   limit is consumed; a later poll returns `410`).
7. On local cancellation, POST `/_allauth/app/v1/auth/social/cancel` with the same
   attempt ID and verifier. `204` is idempotent. It deletes any unclaimed session
   and browser state. A late cancellation after a successful claim does not
   sign out that already handed-off session; use the normal session DELETE.

The desktop completion page contains no account details or credentials. iOS uses
`ASWebAuthenticationSession` with callback scheme `clarify`. After the provider
callback the server redirects through a fixed completion path to exactly
`clarify://auth/complete`, with no query, fragment or credentials. The callback
only wakes the app; the PKCE-protected poll determines the result. No browser URL
contains a Clarify session or native verifier. The launch URL is an opaque,
single-use browser invitation; do not share it or record it in access logs.

The native allauth session is copied into a separate database session and cannot
be used before the protected claim. The OAuth browser session, including any key
rotated by allauth, is deleted in the same callback. Browser cookies never retain
the native session. Unclaimed sessions expire at the attempt deadline; native
claim restores the standard session lifetime. Cancellation, expiry checks and
bounded maintenance revoke abandoned sessions. Start and normal API maintenance
remove expired attempt rows. A quiet service still rejects expired session data.
All state changes use a PostgreSQL row lock, including the provider callback,
claim and cancellation, so concurrent requests have one winner.

Polling uses its own limits (120 requests per peer/minute and 2,400 global/minute)
and a five-second pending interval per attempt. It does not consume the email
authentication limiter. Start allows six attempts per peer/minute in addition
to the existing authentication limit. A reverse proxy's shared peer can limit
several users; retain the existing trusted-ingress policy before widening limits.

## Acceptance gates

Automated tests mock provider HTTP and exercise real allauth redirect, callback,
signup and native session flows. PostgreSQL tests cover simultaneous claims and
cancel/claim races. Automated checks do not establish provider registration or
native browser acceptance.

Before enabling each provider, check in staging with controlled test accounts:

- Exact callback registration, HTTPS origin, consent screen, requested scopes,
  provider code exchange and PKCE acceptance. No real provider account has been
  created or changed by this implementation.
- Google verified and unverified addresses; Microsoft personal and organizational
  accounts through `common`, including the Clarify email-code continuation;
  GitHub private/public, verified/unverified and unavailable email cases.
- Desktop system-browser return and safe completion page; physical iOS
  `ASWebAuthenticationSession` completion and user cancellation. Check the app's
  callback scheme registration and that the app polls instead of trusting a URL.
- Existing email account collision directs to email login without linking;
  closed signup, account limits, disabled users and daily email quota fail closed.
- Wrong verifier/state, another browser, expired/cancelled/replayed attempts,
  abandoned-session revocation, browser-cookie isolation, native logout and
  administrator host/session separation.
- No provider secrets, native tokens, launch URLs, OAuth codes, state values or
  email codes in proxy/application logs, analytics, recordings or crash reports.

Provider console setup, live consent, real SMTP, device acceptance, client
integration and deployment remain explicit release gates.
